# W2 里程碑技术批判（task113~123 批次，2026-09-04）

> 批判者：编排者（traework 独立上下文子 agent，受 tt 工作流派发）。人设：以同类顶级竞品为唯一批判根据，故意挑刺。每条含问题/竞品对标/证据/差距/优化方向/最小验证/收益成本。批判基于真实 commit 与源文件逐行核实（见各条「证据」）。

## C1 响应壳"全站统一"是运行时兜底而非契约形态，文档与运行双源漂移

- **问题**：task114（commit bdf85cd）用 RespWrap 中间件包壳后宣称"响应壳全站统一（C-A 冻结）"，但"统一"只存在于运行期中间件这个黑盒里：
  1. `/api/users/me/profile` 等端点仍以裸 `response_model=UserProfile` 声明（edu-agent/app/users/router.py:24、31），OpenAPI `/docs` 文档标注的是**裸 DTO**，而运行期被中间件包成 `{code,message,data}`——**文档与运行不一致**，下游按文档对接会写错解析器。
  2. 全站是"两套壳来源"混用：部分端点手写 `ok()` 壳（users/router.py:68 等）、部分裸 DTO 靠中间件兜底（resp_wrap.py:74-80），契约形态没有一个地方是"类型/文档"强制的，靠"三键齐备"启发式判幂等（resp_wrap.py:127-133）与白名单 (`/health`、`/metrics`、`/docs`) 显式排除。
  3. 前端 edu-api.js 仍保留"裸 DTO 原样返回"兼容分支（edu-frontend/public/edu-api.js:140-145，注释"裸 DTO（如分页壳）"）——前端"每页双解析"并未彻底终结，只是转移到了 client 兼容层。

- **竞品对标**：JSON:API 规定**单一、一致、可进文档校验**的 document 结构，顶层 `data/errors/meta` 是唯一形态，客户端与服务端据此一次性对接（https://jsonapi.org/format/#document-top-level，访问日期 2026-09-04）；OpenAPI 契约要求 declared response shape 与运行响应一致，否则客户端/自动化测试按文档生成的解析器直接失效（https://spec.openapis.org/oas/v3.1.0，访问日期 2026-09-04）。竞品的"统一"是**契约层**统一（文档可证伪、可 codegen），我们的是**实现层**统一（黑盒兜底、只可运行时试）。

- **证据**：commit `bdf85cd`（task114）；`resp_wrap.py:30-33`（白名单）、`74-80`（2xx 包壳）、`127-133`（三键幂等）；`users/router.py:24/31/68`；`edu-api.js:140-145`；契约单 `handoffs/task114-contract.md`。

- **差距**：竞品的统一经得起静态与 codegen 校验；我们的统一**静态不可证**——下次新增端点只要忘了壳，中间件会兜住成功态但文档仍显示裸体，无人能在合并时发现偏差；OpenAPI 消费者（未来 CDC/L1 codegen）会被 `response_model` 误导。

- **优化方向**：把"壳形态"从黑盒中间件**上移到契约声明**——对全站 `response_model` 统一包 `Shell[T]`（或 `response_model=None` + 中间件），并让 OpenAPI 生成器输出包壳形态（自定义 `app.middleware.resp_wrap` 的 schema transform）；逐步把裸 DTO 端点显式改为 `ok(data=...)`，让中间件从"必需品"退化回"非契约健康检查/兜底"。排队进入 C-A 迭代二。

- **最小验证**：`GET /api/users/me/profile` 的 `/docs` 展开形态 = `{code,message,data:{UserProfile}}`（而非当前裸 UserProfile）；对 `git grep "response_model="` 中仍裸 DTO 的端点清零或显式豁免。

- **收益/成本**：消除文档↔运行双源漂移，打通 codegen/CDC 前置条件 / 涉及全站 schemas 收敛，属底层改造，建议随 socket/system 重构批次评估，非一行改动。

## C2 分页"双轨"兼容窗口长期保留 page_meta，过渡期承诺未设硬截止

- **问题**：task115（commit aaf6456）把课程域列表改为 `{total,page,page_size,items}` 但**同一 DTO 里继续保留 `page_meta`**（返回 `page_meta` 又返回外层 triple），声称"兼容窗口下一迭代删除"。问题在于：①每页 payload 双写一组元数据（total/page 各存两遍，浪费带宽且测不出谁权威）；②前端需知道"权威字段"切换时序，处于过渡期的页面（courses.html 曾读 page_meta）与新字段并存，极易出现"新前端读老字段"或反之的隐性错读（task115 风险自认）。

- **竞品对标**：JSON:API 分页是**单一来源**——**要么** `page[size]` 查询参数、**要么** `links`/`meta` 派生，响应不再冗余双轨（https://jsonapi.org/format/#fetching-pagination，访问日期 2026-09-04）；DRF `PageNumberPagination` 的响应只有一条聚合通道，无"双源同值"概念（https://www.django-rest-framework.org/api-guide/pagination/，访问日期 2026-09-04）。竞品用「单一响应 + 向后兼容用别名参数而非冗余字段」不留长期双写。

- **证据**：commit `aaf6456`；`domains/course/schemas.py:52-64`（`SeriesListData` 同时含 `total/page/page_size/items` 与 `page_meta:PageMeta`）；`domains/course/service.py:64-71`（`_build_page_meta`）、`121-128`（同时组装两套）；`domains/course_admin/schemas.py` 全系 `page_meta` 并存；契约单 `handoffs/task115-contract.md`。

- **差距**：竞品的兼容期靠类型/别名/单一权威解决；我们用"双字段同值"做过渡，埋下**漂移 + 前端选错字段**两重风险，且无自动化断言强制到期删除。

- **优化方向**：给兼容窗口设**硬截止与门禁**——把`弃用时间表`写死进契约单并挂 W4 全量回归门禁：回归中 `git grep "page_meta"`（前端）=0 且后端 `SeriesListData` 删除该字段后必须绿灯，否则计数为里程碑 FAIL；替代过渡手段改为「查询参数别名」而非响应冗余字段。

- **最小验证**：W4 回归断言 `grep -c "page_meta" edu-frontend/public/*.html` = 0 + `courses.html` 只读外层 triple；后端 `schemas.py` `page_meta` 字段删除后 `interface_acceptance_final.py` 全绿。

- **收益/成本**：消冗余带宽与漂移风险，明确权威单一 / 字段清理是一次性低风险删除，主要成本在看门禁是否强制执行。

## C3 chat SSE error 只覆盖 token 迭代段，错误面不完整（检索/落库/初始三段仍走老路）

- **问题**：task115（commit aaf6456）给 SSE 加了 `error` 事件，但**只在 token 迭代这一个 try/except 里发**（chat/router.py:244-255），且错误码硬编码为 `INTERNAL_ERROR`（50000），把 LLM key 失效/限流/超时全部压成一句「答案生成失败：{type}」。另外三段仍不在 error 事件范围内：
  1. 连接前初始化/检索失败 → 走普通 HTTP 错误（router.py:205-223），前端须在 SSE 事件与 HTTP body **两个通道**分别解析失败；
  2. `RETRIEVAL_DONE` 阶段（如果检索逻辑后移到生成器内）无包裹；
  3. 落库 `build_finalize` 失败（router.py:258-271）**故意不报 error**，只塞进 `degraded_reason`——持久化失败对用户透明静默。

- **竞品对标**：WHATWG Server-Sent Events 规范要求事件流用**统一的事件分发 + error 处理模型**（EventSource 的 onerror 与事件解析一致触发），不允许"部分失败走 HTTP 头、部分失败走流内、部分失败静默"三种并存（https://html.spec.whatwg.org/multipage/server-sent-events.html，访问日期 2026-09-04）；主流流式 LLM 网关对"流已建立后的任何失败"都发结构化终止帧（带可区分错误码）而非静默降级。

- **证据**：commit `aaf6456`；`chat/router.py:205-223`（初始化错误 → HTTP）、`233-241`（RETRIEVAL_DONE 无包裹）、`244-255`（仅 token 迭代 error + 硬编码 INTERNAL_ERROR）、`258-271`（落库失败静默进 degraded_reason）。

- **差距**：竞品的失败是"流内结构化、码可区分、时序明确"；我们的失败分三通道且 token 段丢失具体下游错误码，**错误可观测性/可排查性不足**，前端 `error` 分支形同"部分可用"。

- **优化方向**：把 SSE 错误模型收敛为**单一贯穿通道**——生成器整体 try/except 统一转 `event:error + {code,message}`（保留具体下游错误码，如 LLM_AUTH/LLM_TIMEOUT），初始化/检索失败在"已建连后"也合并进来；落库失败升级为显式 error（或契约明确其语义并给前端提示）。与 C3 现有 `error` 事件合并完善而非新增。

- **最小验证**：注入强制检索失败 → 流内收 `event:error`（而非空 HTTP 400/500）；注入落库失败 → 不再静默 degraded_reason。回归 chat 流式冒烟（token 正常）。

- **收益/成本**：错误面统一、可观测性显著提升 / 生成器重构范围小，主要成本是前端 error 分支渲染增强。

## C5 删除语义"软删+真删+40908 拒引用"三态太难消费，且软删实现与权威竞品模式对不上

- **问题**：task116（commit e52d70f）落定的删除形态是**软删（sale_status=off_sale + yn=0）+ `?include_deleted` 回收站参数 + `?hard=true` ADMIN-only 真删 + 40908 拒引用**三态并存。复杂度高：同一条 `DELETE /series/{id}` 的语义随 `?hard`/角色在「下架/软删/真删/报错」之间跳变；管理端普通操作员（manager）无法真删却要理解硬删存在；`?include_deleted` 只见参数未见回收站 UI（task116 自认"本期只留参数,不建 UI"），用户侧根本无"已删除可恢复"的入口，软删带来的可恢复性被浪费。

- **竞品对标**：权威软删实践是**单一删除语义 + 显式垃圾回收站/恢复端点**，硬删是独立、极少用、必须显式（如 API 子资源 `:restore`/`trash` 端点、管理员专属 hard-delete，见 django-safedelete 的 `deleted_only`/`restore` 与 `HARD_DELETE` 策略：https://github.com/cerstensoftware/django-safedelete 的等价实践 https://certidevs.com/tutorial-django-api-rest-soft-delete，访问日期 2026-09-04）；企业级更把软删收敛为"retention window + 自动转硬删"，避免删除语义在应用层三态长期残留（Microsoft Entra "soft delete then purge" 模式：https://github.com/MicrosoftDocs/entra-docs/blob/repo_sync_working_branch/docs/backup/soft-deletion.md，访问日期 2026-09-04）。

- **证据**：commit `e52d70f`；`domains/course_admin/router.py:84-93`（`admin_delete_series`，`hard` query + `me.role != ADMIN` 判定 + `delete_series`）；`schemas.py:4-5`（软删语义注释）；契约单 `handoffs/task116-contract.md`（40908）；前端 admin-courses 删除弹窗文案改"下架"（task117）。

- **差距**：竞品的三态由「资源→回收站→恢复→(保留期后)真删」的**用户可操作闭环**表达；我们是**参数迷宫 + 无 UI + 双角色规则**，前端只能猜，软删的可恢复优势没有落到可触达的产品功能上。

- **优化方向**：本阶段先固化管理员回收站最小闭环（`include_deleted` 已有 → 补 `POST /series/{id}/restore` 恢复端点 + admin-courses 回收站 Tab），把 `?hard=true` 标记为 UI 不可达的运维操作并在文档标注；优先级低于 W4。

- **最小验证**：admin 软删一条 → 回收站可见 → restore 后可重新上架；hard 有引用仍 40908。GWT 回归现有 6 步不走样。

- **收益/成本**：三态有闭环可触达、减少前端语义猜测 / 需新增 restore 端点 + 回收站 UI，中等成本。

## C6 practice 判分只覆盖三题型，其余 FILL/DRAG_SORT/MATCH 置灰"迭代二"——功能裁剪未配主流程说明

- **问题**：task120（commit 9188212）把复习判分接到后端 `quiz/next→submit`，但**只支持 SINGLE/MULTI/JUDGE**，FILL/DRAG_SORT/MATCH 题型入口 `opacity:.45` + `title="迭代二暂不支持"` 置灰（practice.html:734-736）。问题：①用户看到错题本里真实存在这些题型的错题，却进不了对应专项/复习，**功能面有不留说明的断层**；②"迭代二"是无日期的口头承诺，无 PBI 承接极易永久滞留；③填空题在 `practice.html` 静态演示态仍有 `data-type="blank"` 题库模型，登录态却砍掉，**演示/真实行为不一致**（与 C4 同源：演示残留掩盖了真实裁剪）。

- **竞品对标**：成熟的在线测验/学习平台把多题型（填空、拖拽、匹配、排序、计算）作为**基础能力全量开放**，而非"剩下待迭代"——Moodle 提供 20+ 题型开箱即用且均有可判分的提交/反馈闭环（https://docs.moodle.org/en/Question_types，访问日期 2026-09-04）；对暂无能力覆盖的题型，竞品用**显式的路由/引导**（跳"该题型即将支持"）而非灰按钮静默。

- **证据**：commit `9188212`；`practice.html:727-736`（`FILL/DRAG_SORT/MATCH` 置灰 + "迭代二暂不支持"）；`practice.html:514-538/586-589/588`（静态演示仍有 blank 题型与 `data-type="blank"`）；task120 完工报告范围节（SINGLE/MULTI/JUDGE）。

- **差距**：竞品"要么全量可用、要么显式引导"；我们"演示里有、登录态沉默置灰"，用户困惑 + 承诺无主。属产品缺口而非纯代码债，但代码层应先把"置灰"改为"显式不可用且有去向说明"。

- **优化方向**：把 FILL/DRAG_SORT/MATCH 的灰按钮改提示弹层"该题型暂未开放，已登记迭代二"（带红点/PBI 链接语义）；在错题本/专项区对这三类题**过滤或标注**，避免"列表有题、按钮点不了"的断层；将"迭代二支持剩余题型"登记为真实 PBI 并给 deadline。

- **最小验证**：登录态专项区三题型不再只是 opacity 裁剪，点击出现明确说明；错题本对未支持题型有 badge 标注而非可看不可练。

- **收益/成本**：消除演示/真实断层与永久承诺 / 前端小改 + 一个 PBI。
