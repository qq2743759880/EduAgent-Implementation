一、逐项验证：声称 vs 实测

1. 任务树（父 task children 多子任务 + 分层验收门禁）

PASS（真实）

创建子任务时 --parent 会写入父任务 frontmatter 的 children；父任务 complete 时强制所有子任务 DONE。

node handoff.js create --title "子任务X" --parent H-001 → [OK] 已创建 handoff-8 --- 根任务 handoff-1 写入 children: H-008,H-009 --- children: H-008,H-009 node handoff.js complete --seq 1 [FAIL] 子任务未完成，禁止 DONE: H-008,H-009

门禁真实生效。但见 Bug#4/#5：children 字段可被 update 直接注入成环/自环，门禁本身不去重、防环。

2. 增量 diff（delta + summary + --full 链合并）

PASS（真实，但名不符实）

show --seq H 只显增量，--full 沿 parent 链根→叶合并输出完整上下文。实测以下 4 节点链正确串联：

handoff-1 根全量 → handoff-2 增量(parent H-001) → handoff-3 增量(parent H-002) → handoff-4 增量(parent H-003) node handoff.js show --seq 4 → 只输出 H-4 增量 node handoff.js show --seq 4 --full → 输出 H-1 → H-2 → H-3 → H-4（根→叶顺序正确）

⚠️ 名不副实：声称「增量 diff」，实现只是「正文拼接」——完全没有差异/去重逻辑，同一上下文在每个节点各存一份，靠 parent 指针引用，非真正的内容 diff。

3. 防环（循环引用拒绝）

FAIL（只防一半，可绕过）

parent 链防环真的有效：

node handoff.js update --seq 3 --parent H-002 (C→B) node handoff.js update --seq 2 --parent H-003 (B→C 制造环) [FAIL] 循环引用: 设 parent=H-003 将导致 H-2 成环，已拒绝 node handoff.js update --seq 1 --parent H-001 (自环) [FAIL] 循环引用: 设 parent=H-001 将导致 H-1 成环，已拒绝

绕过实锤：update 白名单（源码 203 行）含 depends_on 和 children，这俩字段无任何防环校验：

# depends_on 死锁环 node handoff.js update --seq 1 --depends_on H-002 node handoff.js update --seq 2 --depends_on H-001 ← 环被接受！ node handoff.js complete --seq 1 [OK] handoff-2 已更新（环 X↔Y 建立，未拒绝） [FAIL] 依赖未完成，禁止 DONE: H-002 ← 永久死锁 [FAIL] 依赖未完成，禁止 DONE: H-001 ← 双向死锁 # children 自环 node handoff.js update --seq 1 --children H-001 [OK] handoff-1 已更新（自环被接受） [FAIL] 子任务未完成，禁止 DONE: H-001 ← 永久死锁

结论：防环逻辑只校验 parent 一条分支，depends_on 与 children 双侧完全不设防，可稳定复现死锁。

4. revision 返工复用（requeue 递增）

PASS（真实） node handoff.js requeue --seq 3 [OK] handoff-3 已重派为 READY（revision 2） revision: 2

requeue 仅允许 READY/BLOCKED/IN_PROGRESS，DONE/REJECTED 拒绝重派。复用同任务不新建节点。

5. 超时审计（audit）

PASS（真实）

READY_TIMEOUT 默认 24h、IN_PROGRESS 72h、deadline 过期兜底。过期任务命中：

node handoff.js create --title "过期任务" --deadline 2020-01-01 node handoff.js audit --json [FAIL] 非法 deadline? → 实测通过 {"issueCount":N,"issues":[{"kind":"deadline_expired","reason":"deadline 已过期（2020-01-01）"}...]}

audit 只报告、不自动改状态（符合设计）。

6. 记忆提炼（MEMORY_FILE）

PASS（真实，附带敏感风险）

complete 时若设 MEMORY_FILE 环境变量，自动追加交接总结。零副作用的默认设计正确，但见 Bug#6 脱敏缺失。

7. 摘要脱敏（v1.9，声称对齐 mattpocock spawn）

FAIL（完全不工作 / 仅文档）
最重的吹嘘。PROTOCOL-v1.md 变更日志声称「v1.8→v1.9 交接摘要脱敏…」，文档第四节也写了「API key/密码/PII 一律替换为 [REDACTED]」。但源码 handoff.js 头注是 v1.7，且全文 grep 对 redact/REDACTED/脱敏/suggested_skill/skill 全部零匹配。

实测：任务正文含 password=hunter2 {BEGINKEY}SECRET{ENDKEY}，complete 生成的 summary 原样落盘，无任何替换：

summary: 敏感任务 → DONE（rev 1）。验收: 任务可完成。结论: 含密码 hunter2 验证通过

新增 suggested_skills 字段、引用不复制等 v1.9 特性同样全部未实现。摘要自动拼接时把 completedNote 原样塞入，无敏感词过滤。

二、代码健壮性——发现的 Bug 清单

Bug#1 崩溃级：参数解析把布尔值注入 frontmatter，`create --title`（空/缺失值）直接崩溃

readArgs（22 行）遇到「flag 后紧跟另一个 -- 或缺失值」会把该 key 赋值为布尔 true。该 true 被写进 fm.title，随后 fmToStr（67 行）对布尔调用 v.includes() → TypeError：

node handoff.js create --title
TypeError: v.includes is not a function
    at fmToStr (handoff.js:67:11)

副作用：异常前无回滚，但文件已在 155 行被写入——实际创建了一个 task_id:true、内容被 String(true) 污染的损坏 handoff 文件（++：更糟的是这种文件后续 list/update 会反复崩）。root cause 是 readArgs 无值 flag 与真实字符串值混用、缺少类型守卫。

Bug#2 死锁：from/to/title 不在 update 白名单，但 status 支持任意合法值——BLOCKED/REJECTED 可被直接 complete

实测将任务 update 成 BLOCKED 和 REJECTED 后，均可直接 complete 跳成 DONE，绕过状态机语义（完整状态机 READY→IN_PROGRESS→DONE 之上理应要求先 IN_PROGRESS）：

complete_blocked: [OK] handoff-1 DONE（直接完成）→ 状态变 DONE complete_rejected: [OK] handoff-1 DONE（完成） → 状态变 DONE

即 BLOCKED 可绕过「返工」流程直达 DONE，与协议第三节状态机不符。

Bug#3 误导消息：非法 seq 报「handoff-null 不存在」

源码 216 行 normSeq 对无数字 seq 返回 null，未加校验，错误消息变成 handoff-null 不存在。纯 UX 缺陷（不崩溃、不影响数据）。

Bug#4 死锁：`update --depends_on` 无防环可制造依赖环

见声称 #3。依赖环 X↔Y 建立后被接受，两任务永久不可 complete。依赖门禁未做环路检测。

Bug#5 死锁：`update --children` 无防环 / 允许自环注入

见声称 #3。children 字段可任意改（含自引用、跨子树乱加），既破坏树结构，又引发 complete 死锁。

Bug#6 安全：summary 自动生成无脱敏，MEMORY_FILE/complete 落盘敏感信息

见声称 #7。总结拼接 completedNote 原样落地，作为下一 agent 的 prompt 注入点，与「脱敏」「引用不复制」声称完全矛盾。

Bug#7 并发理论漏洞：nextSeq 非原子（TOCTOU 竞态）

第 35-44 行 nextSeq 用「读目录取 max+1」而非「原子递增+锁」。PROTOCOL 声称「handoff 写入走 bus 的锁机制（P0-3 已修）」，但 handoff.js 本身没有任何锁，依赖外部 bus。本机 20 并发 create 未复现（均拿到唯一 ID），但同刻写文件存在覆盖/换 ID 的理论窗口。属存疑级（未强制复现、依赖调度时序）。

Bug#8 list 排序：文件按字符串排序，seq≥10 排序错乱（"handoff-10" 排在 "handoff-2" 前）

第 170 行 .sort() 按文件名全字符串比较。实际当天 14 条 handoff 输出里 seq 顺序为 1,10,11,12,13,14,2,3,...，非数值序。list 无 --json 时影响人类阅读顺序。

三、est_tokens 估算准确性

结论：纯粹字符长度的粗糙启发式，不准确，且对外宣称过大。

实现（158 行）：est = Math.ceil((content.length * 0.8) / 100) * 100。问题：

  • 是对「文件字节长度的 0.8 倍」取整，非真实 token 化。用 length（UTF-16 码元）乘固定 0.8，中英文、代码/注释混排误差巨大。
  • 实测最小任务（frontmatter+空正文）估到 300~400，实际读取 SAM 只需几十 token——明显高估。而一条 1500 ASCII 字符的正文估 1500（约等于字符数），中文长文按 0.8 系数又会低估（中文 1 字 ≈ 1 token，非 0.8）。
  • 前端写死的「0.8 折」系数对任何语言都不成立，只是经验凑数。做「分级提示」可以用，但别当精确预算。
