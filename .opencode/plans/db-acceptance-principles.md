# 数据库验收体系设计原则（6 点，用户 2026-08-17 定稿）

> **性质**：最高优先级设计原则，约束所有数据库相关任务（建表/改表/数据重灌/生产发布）的验收设计。
> **适用范围**：task07 建表验收标准**保持现状不改**；**后续所有数据库迭代任务的验收标准必须按本 6 点原则设计**。
> **复用性**：本体系为可复用基础设施，生产环境用户注册、增添功能、修改表结构时均沿用。

## 6 点验收原则

### P1 代码实现文档，文档定义标准 → 先改文档，再改脚本
- 任何验收标准变更，**先更新 GWT 文档/契约文档，再改校验脚本**，顺序不可反。
- 文档是唯一权威：脚本必须忠实实现文档，脚本与文档不一致 = 脚本 bug。
- 落地：每次改表/加功能，先修订 `tasks/` 或独立契约文档，再同步脚本。

### P2 精确断言，不是下限检查 → 用 ==，不用 >=
- 验收必须断言**精确值**（`==`），禁止用 `>=` 下限放水。
- 例外需显式声明：如 sys_user≈10万 这种"数量级目标"才允许区间，且区间必须来自文档（±0.5% 由文档定义），不可执行方自定。
- 落地：校验脚本断言为 `actual == expected` 或 `abs(actual - expected)/expected <= DOC_TOLERANCE`（tolerance 从文档读）。

### P3 动态计算，不写死 → 从数据库/权威源获取，不从配置文件硬编码
- 期望值必须**动态计算**：机构数 `SELECT COUNT(*) FROM org_institution`、模板数从种子权威源（series.csv）或生成逻辑推导。
- 禁止硬编码 `INSTITUTIONS = 6`、`SERIES_COEFF = 2` 这类魔数——一旦机构数变化脚本即失真。
- 落地：期望值 = f(权威源)，权威源 = edu.sql + seeds + 生成配置，不是目标库 count 自我推导（避免循环验证）。

### P4 CI 是门禁，不是提示 → 校验失败，禁止合并
- 校验脚本接入 CI：失败 = 构建/合并阻塞（exit code != 0），不是黄色警告。
- 覆盖：DDL 变更、计数断言、5 维度质量检查全部进 CI gate。
- 落地：GitHub Actions / 本地 pre-merge 脚本，`verify_schema.py` / `verify_quality.py` 非零退出即拒绝合并。

### P5 数据质量 5 维度全验 → 完整性、唯一性、有效性、一致性、时序性

| 维度 | 检查内容 | 状态 | 示例 |
|------|---------|------|------|
| 完整性 | 外键无孤儿 + 引用必达 | ✅ 已有(外键) / **补：支付引用** | order.payment_id → 全部指向真实 payment_record |
| 唯一性 | 唯一键 + **逻辑重复** | ⚠️ 部分(唯一键) / **补：逻辑重复** | 两个不同 ID 指向同一用户/同账号 |
| 有效性 | 值域合法 | ❌ 未查 | 金额>0、状态在合法枚举、日期不在未来 |
| 一致性 | 跨表数值守恒 | ❌ 未查 | order.amount = SUM(order_item.amount)、payment.amount = order.amount |
| 时序性 | 时间先后合理 | ❌ 未查 | created_at <= updated_at、start_date <= end_date |

每维度至少 1 条 SQL 断言，全绿才算「数据基线冻结」。

### P6 声明口径漂移 → 任何标准变化，必须显式声明并更新文档
- 任何验收口径/标准的变更（如 219→6 机构），必须：① 更新文档（GWT/契约）② 记录变更日志（版本+日期+理由+实证）③ 同步脚本 ④ 报告里显式声明"口径已变更"。
- 禁止执行方静默改口径；口径变更须编排者确认。

## 可复用生产验收体系（落地形态）

后续由独立 task（见 dev-plan）实现为可复用框架，生产环境复用：

```
verify.py 统一入口（可复用，非 per-task 一次性脚本）
├── schema   → 结构校验（66 表 DDL vs information_schema，0 差异）
├── counts   → 计数断言（精确 ==，期望值动态计算自权威源）
├── quality  → 5 维度质量（完整性/唯一性/有效性/一致性/时序性）
└── all      → 全量（CI 门禁入口，任一失败 exit 1 禁止合并）
```

- 配置从数据库/权威源动态读取（机构数、模板数、枚举字典）
- 容差阈值从文档定义（.schema-acceptance.yaml 或契约文档），脚本读取
- CI：GitHub Actions workflow 调用 `verify.py all`，失败即 gate
- 生产发布流程：改表前跑 schema 预检 → 改后跑 all → 计数+质量双绿才可发布
